# Autoresearch plugin

A **study** improves one metric of a codebase over hours or days. The plugin runs the loop: it spawns short-lived hidden **worker** threads (one idea each, in their own worktree branched from the study's best), measures every submitted candidate against `best` on its own oracle, and promotes only statistically real wins. Agents propose; the plugin decides.

## Commands (humans run these)

| Command | What it does |
|---|---|
| `bb study list` | Studies (active first): state, what needs the human, best vs base, candidates, bench time |
| `bb study needs [slug]` | What needs the human (approvals, system pauses, failures, a frozen harvest), one line each with the command that resolves it |
| `bb study show <slug> [--events N]` | Needs you, best vs base, spec, budget, guardrails, bench, calibration, ideas, last candidates, workers, notices, recent events |
| `bb study calibrate <slug> [--wait]` | Approve the current (or pending) spec; run gates and A/A noise measurement on every bench host. Mid-run this is an oracle change: new segment |
| `bb study approve <slug>` | Apply a pending spec whose oracle is unchanged (budget, agents), without recalibration |
| `bb study start <slug>` | Approve calibration and start running (or resume) |
| `bb study bench <slug>` | Bench hosts (remote machines too: state, expiry, rotation, own calibration): health checks, git bundle transfers, drift checks, segments |
| `bb study drift <slug>` | Run a drift check (A/A on best) on every bench host at its next free slot |
| `bb study pause <slug>` / `resume <slug>` | Pause: no new workers; running workers finish their submission |
| `bb study concurrency <slug> <n\|auto>` | Lower the worker limit below the spec's `max_workers` (requests above it are clamped), or return to the spec's value |
| `bb study ideas add <slug> "<title>" [--rationale --theme --priority --start-ref c/N --variation-of ID --no-pin]` | Queue (and pin) an idea |
| `bb study ideas list <slug>` | The idea board |
| `bb study workers <slug>` | Worker threads and their state |
| `bb study archive <slug> [--archive-thread]` | Stop workers, archive their threads, remove bench checkouts (git refs kept); `--archive-thread` also archives the study thread |
| `bb study harvest <slug> [--wait] [--harvest N]` | Freeze best for harvest: no new workers, submissions closed, in-flight candidates finish, then best is pinned as `refs/studies/<slug>/harvest/h<N>`. An agent then harvests it (the `study-harvest` skill). With a frozen harvest it shows it; `--harvest N` shows an older one (read only) |
| `bb study evidence <slug> [--json] [--samples] [--candidates 3,7]` | Everything needed to harvest, as stable JSON (`bb-autoresearch/evidence` v1): candidates (refs, commit messages, diff stats, verdicts, effects, guardrails, findings), promotions on best, segments, bench hosts, base/best/frozen, and the runs below |
| `bb study measure <slug> <A> <B> [--pairs N] [--host H] [--detach]` | Measure B against A (any two commits) with the study's protocol and guardrails, under the bench lock, on the quietest free bench host and with that host's own win threshold (a remote-only study frozen for harvest waits for its machines); counts as bench time. Refs: a sha, branch, `best`, `base`, `c/<n>`, `best~1` |
| `bb study gate <slug> <ref> [--detach]` | Run the study's gates on any commit (edit host) |
| `bb study results <slug> [r<N>] [--wait]` | The measurements and gates asked for, or one in full |
| `bb study report <slug>` | The study report in Markdown |

Every command takes `--json` and then prints one JSON document built from the same view models as the Studies page (`list` → `{ studies }`, `show` → the overview, `needs` → `{ total, studies: [{ slug, needs }] }`, `bench`, `harvest`, `ideas list` → `{ ideas }`, `workers` → `{ workers }`, `report` → `{ markdown }`, `measure`/`gate`/`results <id>` → `{ run }`, `results` → `{ runs }`, `evidence` → the evidence document (or `{ format, version, file, bytes }` when it is too large for one response: the whole document is in that file), controls → `{ ok, message, study }`). Errors come as `{ ok: false, error: { code, message, hint } }`; the hint names the command to run next. Improvements read the same everywhere: positive is better in the metric's own direction ("20.0% lower size", "c/3 win +4.2% (CI +3.7% to +5.2%)"); a measurement's effect is B relative to A.

The **Studies** page in the BB sidebar is the primary surface: every control above is there too, including the deliberate steps (approve a spec and calibrate, approve the calibration and start, freeze best for harvest, archive), each behind a dialog that says exactly what will happen. Its Overview leads with **Needs you** (pending approvals, system pauses, drift alarms, failed calibration, a frozen harvest waiting for an agent); the sidebar entry and the study thread's header badge show how many items wait. In-app and CLI approval are equivalent and audited the same way. Study and worker threads show a header badge with live status. While a study runs, the page opens on its read-only **Live** tab (worker lanes and phases, candidates moving through tests and the bench, verdicts, the bench, the ideas up next, a feed, one worker's transcript at a time); the study thread's header badge has a **Live** button that opens the same view beside the thread (also "Study live view" in a thread's right-panel launcher). It also shows each measurement's CI band narrowing pair by pair against the win threshold until the sequential test stops, a short "last action" per worker, and the moment best moves. Any study can be **replayed** (Live tab → Replay, the Overview's Replay button, or the side panel's Replay switch; the page URL `<slug>/live/replay/<ms>` reopens a moment). If the human asks how to watch or review a study, point them there. Workers' phases and last actions ("editing src/x.py", "running pytest -q") come from the tool calls their threads make (kind, command, tool name, file paths, shortened and with secrets removed), never from message text.

In the study thread, plugin messages show one line to the human (for example "Strategist round 3 (new verdicts): 2 new verdicts (1 win, 1 lose), best now 47% fewer ops vs base · 4 ideas queued"); the full digest or verdict detail is an agent-only block that you still receive in full.

`calibrate`, `approve`, `start`, `pause`, `resume`, `concurrency`, `drift`, `harvest` (freezing; showing a frozen harvest is a read), and `archive` are human controls: the plugin refuses them from a study's own worker or strategist thread. `measure` and `gate` are not: any thread may ask (the study thread included) except a study's workers; each request is recorded as a `control.measure`/`control.gate` event with the caller, and its result as `measure.adhoc_finished`/`gate.adhoc_finished`. They are refused while the study runs workers and its bench is busy (a candidate testing, queued or measuring): freeze it for harvest first. A paused study whose bench is remote only has no machines (pausing destroys them): freezing brings them back. `evidence` and `results` are reads. If the user asks you to run one, you may, from an ordinary thread. Every control change is recorded as a `control.*` event and a notice, with the caller and any study agent turns running at that moment.

## Lifecycle

Draft (spec proposed with `study_propose`) → Calibrating (`bb study calibrate`) → Running (`bb study start`) ⇄ Paused → Harvesting (`bb study harvest`: best frozen for an agent to harvest) → Running again (`bb study resume`: keep exploring) or Archived. Running → Calibrating again when the human approves an oracle change; that starts a new **segment** (`refs/studies/<slug>/segment/<k>` pins its baseline). When best's runs get much shorter than at calibration (below `oracle.drift.recalibrate_below`, 60%), the plugin recalibrates on best by itself at the next free bench slot: a new segment with the same oracle, no approval, no pause, and a `segment.recalibrated` notice (informational). Best vs base compounds every segment's promotions ("81.8% lower time (5.5×) across 3 segments"); raw values are the current segment's. A clear loss (a 99% t interval entirely below 0) can stop from 3 pairs. Calibration failing (gates red on base, oracle too noisy) returns a new study to Draft; a failed mid-run recalibration keeps the old spec and pauses. Calibration fails when a guardrail can't be judged (its CI at a full evaluation is not narrower than its limit), naming the fixes. An automatic recalibration that finds a bench host unhealthy tries again every `oracle.health.retry_seconds`, up to `recalibration_retries` times, before it pauses the study. The system pauses a running study itself when the budget is exhausted, the oracle breaks (best fails to build or measure, the holdout fails on best), a drift check finds noise above 2× the calibrated level at the same run time (while it is paused for drift, nothing more is measured on that host), the host keeps failing, or the study thread goes away. A bench host that fails its health check or goes offline only defers measurements on that host; the human is notified after a grace period. It records a notice (study page, `bb study show`), marks the study thread unread without starting a turn, and includes the notice in the next strategist round.

## Verdicts

`win` (promoted: squashed onto `studies/<slug>/best` with the worker's own commit message plus the plugin's `Autoresearch-Study` and `Autoresearch-Candidate` trailers; it passed confirmation, or skipped it because its CI's low end was several times the win threshold, and, when configured, the hidden holdout), `lose` (worse, broke a guardrail, or failed the holdout; a guardrail breaks when its CI is entirely beyond its per-step limit against best or its total limit against the segment base; a CI that straddles a limit is flagged inconclusive, not a rejection), `inconclusive` (did not clear the minimum detectable effect; the test also stops early once the CI's high end is below the win threshold, because more pairs couldn't make it a win), `gate_failed`, `conflict` (no longer applies onto best; the worker rebases and resubmits, and the first two conflicts don't count against its submission limit), `rejected` (touched protected or out-of-scope paths, or too large). Candidates are rebased onto best automatically when best moves; a win measured against a best that moved is measured again before promotion. Every candidate is kept as `refs/studies/<slug>/c/<n>`. Nothing is pushed.

## If you are the strategist (the study thread)

Messages starting with `[autoresearch] Strategist round` carry a digest: recent verdicts, findings, the idea board, best's diagnostics, the dossier, budget. Each round:

- read code at best, not in your own checkout: your environment is whatever was picked when the study was created (often a worktree of the project's default branch), so it may be on another commit. Each round's "Code" block names the study base and `studies/<slug>/best` with their commits. Read best without switching branches, from any checkout of the same repository (refs are shared across its worktrees): `git show studies/<slug>/best:<path>`, `git grep -n <pattern> studies/<slug>/best`, `git diff --stat <base>..studies/<slug>/best`, `git log --oneline <base>..studies/<slug>/best`. If your checkout isn't a worktree of the study's repository, add `-C <study repo path>` (the block gives that form). Don't check out or commit in your own checkout.
- keep the idea queue full and diverse: `study_queue_ideas` (title, rationale, theme, priority, optional `start_ref` like `c/12`, optional `variation_of`). At most ceil(W/2) workers run one theme at once.
- lost ideas are never assigned again; an idea that repeats a lost one's title is skipped unless you set `variation_of` to the lost idea's id and say what is different
- retire dead directions: `study_retire_idea`
- keep the dossier current: `study_update_dossier` (workers get it in their brief)
- look things up: `study_search_findings`
- watch the guardrail headroom line: each guardrail's room left under its total limit against the segment base. With little room left, prefer ideas that don't cost that guardrail, or that win some of it back; a win that would push best beyond the total limit is rejected
- relay any "Notices for the human" in one or two lines, pointing to the Studies page for anything that needs them
- reply to the human in two or three short lines (what changed, what you queued, anything they should decide) and end your turn
- write improvements the way the plugin does: better is positive, in the metric's own terms ("12% lower p99")

When the human asks you to harvest the study (turn its wins into PRs), follow the `study-harvest` skill: you do the grouping, branches and PR descriptions with the repository's own tools, and every number and check comes from `bb study measure` and `bb study gate`. Publish only when the human says so.

You never edit code, run benchmarks, or decide verdicts. Concurrency, budget, the oracle, and pausing belong to the human.

The holdout is secret: verdicts say only "passed/failed the holdout check". Never try to find or reproduce the holdout workload.

## Harvest

Harvest freezes best: in-flight candidates finish, new submissions are refused, and best is pinned as `refs/studies/<slug>/harvest/h<N>` (it stays pinned if the study resumes). The plugin does nothing more: an agent turns the frozen best into PRs with the `study-harvest` skill, reading `bb study evidence`, measuring with `bb study measure`, gating with `bb study gate`, and publishing with the repository's own tools only when the human asks. The study optimized its benchmark, nothing more: whether that benchmark represents production is the human's call, so PRs say what was measured. Harvests the plugin ran itself before 1.0 (changesets, ablations, PR drafts) stay readable on the Harvest tab and with `bb study harvest <slug> --harvest N`.

## Budgets and provider limits

`max_candidates`, `max_bench_hours`, `deadline`, and optional `max_tokens` (per-thread token usage as BB reports it) are enforced; reaching one pauses the study and proposes a harvest. Shares in `notify_at` raise a notice once. A rate-limited turn is retried at the provider window's reset (up to `max_rate_limit_retries`), and no new worker starts until then; a provider usage window above `usage_tight_percent` halves W.

## Constraints

- Up to `max_workers` workers at once; W adapts as min(max_workers, ceil(think/eval)+1), and no worker spawns while the bench queue is at least W deep.
- The server's own machine is the edit host (workers, gates). Bench hosts are `local` (plugin checkouts here), BB machines with their own clone, fed by git bundles, or **remote machines** lent by a bench provider plugin (`[[oracle.remote_bench]]`); each bench host decides with its own calibrated win threshold (never below `min_effect`), and queued candidates go oldest first to the quietest free, online and healthy host (lowest threshold first). A host much noisier than the others (`oracle.max_host_noise_ratio`, 2× their median noise floor by default, and beyond chance) is left out: a remote machine is replaced, a local or BB host measures nothing until the next calibration.
- Each `[[oracle.remote_bench]]` entry chooses its machines: `cores`, and `machine = { ... }` with the provider's own options (machine type, SMT, CPU platform, image), passed to it verbatim and part of the oracle hash; `bb study bench` shows what was asked for and what each machine reports.
- Remote machines join (seed upload, shallow repository, setup), calibrate on arrival (each its own noise floor and win threshold, never below `min_effect`; one much noisier than the other hosts is replaced), and are replaced before their lifetime ends: the replacement calibrates first, then the old machine takes no new work and is destroyed once idle. A machine that leaves (suspended, gone, failed) has its measurement restarted elsewhere. They are destroyed when the study pauses or is archived (and come back when it resumes or is frozen for harvest); a plugin reload keeps calibrated machines and re-adopts them; `bb study bench` shows each one's state, expiry, rotation and calibration. A seed with anything credential-like is refused before any machine is created (the notice lists what matched). With `gates = true` the gates run on those machines.
- `noisy` and `expensive` oracles take the bench lock: one measurement at a time per bench host; gates run in parallel outside it, except in single-machine mode (`oracle.single_machine`, on by default when a bench host is the edit machine): then gates take that lock too, in one oldest-first queue with measurements, so a gate never overlaps a measurement, and T_eval is gate + measure time. With `oracle.quiet_bench`, a new worker turn on that machine waits (for at most one measurement) while a measurement runs.
- The spec lives in plugin storage, not the repo. Proposing a revised spec after start makes it pending until the human approves it (`approve` without an oracle change, `calibrate` with one).
