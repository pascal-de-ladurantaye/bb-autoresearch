# Budgets, scheduling and bench hosts

Read before explaining budgets, provider limits, host selection, remote-machine lifetimes, drift or recalibration.

## Budgets and provider limits

`max_candidates`, `max_bench_hours`, `deadline`, and optional `max_tokens` (per-thread token usage as BB reports it) are enforced; reaching one pauses the study and proposes a harvest. Shares in `notify_at` raise a notice once. A rate-limited turn is retried at the provider window's reset (up to `max_rate_limit_retries`), and no new worker starts until then; a provider usage window above `usage_tight_percent` halves W.

## Constraints

- Up to `max_workers` workers at once; W adapts as min(max_workers, ceil(think/eval)+1), and no worker spawns while the bench queue is at least W deep.
- The server's own machine is the edit host (workers, gates). Bench hosts are `local` (plugin checkouts here), BB machines with their own clone, fed by git bundles, or **remote machines** lent by a bench provider plugin (`[[oracle.remote_bench]]`); each bench host decides with its own calibrated win threshold (never below `min_effect`), and queued candidates go oldest first to the quietest free, online and healthy host (lowest threshold first). A host much noisier than the others (`oracle.max_host_noise_ratio`, 2× their median noise floor by default, and beyond chance) is left out: a remote machine is replaced, a local or BB host measures nothing until the next calibration.
- Each `[[oracle.remote_bench]]` entry chooses its machines: `cores`, and `machine = { ... }` with the provider's own options (machine type, SMT, CPU platform, image), passed to it verbatim and part of the oracle hash; `bb study bench` shows what was asked for and what each machine reports.
- Remote machines join (seed upload, shallow repository, setup), calibrate on arrival (each its own noise floor and win threshold, never below `min_effect`; one much noisier than the other hosts is replaced), and are replaced before their lifetime ends: the replacement calibrates first, then the old machine takes no new work and is destroyed once idle. A machine that leaves (suspended, gone, failed) has its measurement restarted elsewhere. They are destroyed when the study pauses or is archived (they come back when it resumes; frozen for harvest, they come up only for requested measurements and gates and are released after `idle_release_minutes`, 10, idle); a plugin reload keeps calibrated machines and re-adopts them; `bb study bench` shows each one's state, expiry, rotation and calibration. A seed with anything credential-like is refused before any machine is created (the notice lists what matched). With `gates = true` the gates run on those machines.
- `noisy` and `expensive` oracles take the bench lock: one measurement at a time per bench host; gates run in parallel outside it, except in single-machine mode (`oracle.single_machine`, on by default when a bench host is the edit machine): then gates take that lock too, in one oldest-first queue with measurements, so a gate never overlaps a measurement, and T_eval is gate + measure time. With `oracle.quiet_bench`, a new worker turn on that machine waits (for at most one measurement) while a measurement runs.
- The spec lives in plugin storage, not the repo. Proposing a revised spec after start makes it pending until the human approves it (`approve` without an oracle change, `calibrate` with one).
